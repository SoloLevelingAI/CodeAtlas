# ADR-0001：先实现显式启动组合，保留旧报告和端口

状态：接受并在第一轮实现。日期：2026-10-18。

背景：旧 AtlasFeature 已支持深层源码功能目录，AddAtlas 已约束声明提供方和单端口注册；二者都没有活动模块/能力/视图的启动协议。PR #1 增加静态证据检查与规范、分工页面，但看见源码属性不等于运行模块已经注册。

决策：在 Contracts 定义只含数据的 ModuleDescriptor、能力需求、Profile 和 ViewContribution；在 Composition 校验模块目录与依赖闭包；在 Runtime 真实接线，在 Host 映射已知视图标识。父级显式指定，逻辑子模块不必拆 DLL。能力兼容策略限定为同接口、同主版本且满足最低版本。

兼容：原 AddAtlas API 和 singleton 行为不变，原 AtlasRuntime.Create 继续返回所需端口。新协议不加入旧报告序列化模型。Web 源码树与运行模块树分别持有展开状态，复用同一个地图实现。

取舍：使用 Type 表达本进程内接口身份，不支持跨进程通用插件清单；Profile 是静态启动选择，不支持热切换容器。必需能力仅在候选唯一时自动选择；多提供方由 Profile 显式消歧。可选模块不会因发现目录而自动启用。

未选择：反射扫描任意 DLL、从字符串构造控件、把全部方法登记成服务、通过菜单隐藏冒充分发裁剪、把运行声明混入源码分析报告。这些会引入额外生命周期或来源歧义，当前需求没有足够依据承担。

后果：获得可测试的首轮启动与交互闭环；仍需独立工作验证物理 DLL 裁剪、客户包资源、授权能力、线程/订阅释放及卸载。静态 AT108–AT111 不证明 Profile 解析或分发闭包；本轮测试分别提供运行证据。
